## Getting at it































The shipped file is **LZEXE 0.91** packed (`LZ91` at offset `0x1C`, a 32-byte















header, no relocations, entry `0771:000e` near the end of the image).















`tools/unlzexe.py` expands it:































    python tools/unlzexe.py work/split/NEUROSIS_008.exe \















                           work/unpack/NEUROSIS_008_unpacked.exe































    image      55056 bytes (3441 paragraphs)















    entry      0000:04b3    stack 1113:4e20















    relocs     772































All 772 relocation sites land inside the image and every stored value is a















small segment number, which is what an unrelocated far reference looks like â€”















the table is sound. `minalloc` is recomputed from `SS:SP` because LZEXE keeps















the original nowhere.































**The one thing that is easy to get wrong** is the bit refill. The stub does































    SHR BP,1 / DEC DX / JNZ + / LODSW / MOV BP,AX / MOV DL,10h































so taking the sixteenth bit pulls the next bit-word from the stream *straight















away*, and a literal or distance byte belonging to that bit is read from after















it. Refill lazily â€” at the next request for a bit â€” and the literal gets handed















the two bytes of the bit-word instead. It decodes perfectly for about seventy















bytes and then walks off the front of the buffer.

## What functions 0 and 1 really are































`1000:01bd` and `1000:020a` — what every part calls `MusicStart` and















`MusicStop` — **install and remove an INT 1Ch hook**. Neither touches the















sound hardware at all.































    INT 1Ch (18.2 Hz)  ->  1000:01a5  ->  1000:0171  ->  4 x Driver.Poll















    function 2         ->                                1 x Driver.Poll































`1000:01a5` chains on to the previous handler with a `JMP FAR` rather than















IRETing, so the BIOS tick is not swallowed. `1000:0171` calls the driver's















poll method **four times over, written out four times rather than looped**,















behind a re-entrancy guard at `DS:$0002`.































So "start the music" means "start letting the timer feed the driver", and















silence on stop is a consequence of the driver no longer being polled. The















names in `src/DEMOVT.PAS` are right about the effect; this is the mechanism.































Both are idempotent — the chain stub's own operand doubles as the "are we















hooked" flag — which is why a part can call `MusicStart` without checking.































## Two chain stubs, no chain variables































DemoVT stores neither displaced vector in a variable. Both INT 1Ch















(`1000:016b`) and INT 2Fh (`1b54:0000`) chain through a five-byte `JMP FAR`















whose **operand** is patched, and both are assembled pointing at themselves.















That is why the uninstall paths read `ES:[DI+1]` and `ES:[DI+3]`: they are















reading the jump's own address bytes.

## The small units



























Six of them, all read end to end.



























**`1544` — the output filter.** `src/VTFILTER.PAS`. Three one-pole IIR













low-passes over a strided 16-bit buffer, and a far entry at `004c` that picks













between them on a strength of 1, 2 or 3. The fractional feedback is done with













`SAR`/`ADC` pairs rather than `IMUL` — `ADC` picks up the bit `SAR` shifted













out, so it rounds instead of truncating, and it is far cheaper on an 8086.













The filter state lives in `BX` across the whole run and is handed back, so a













buffer can be filtered in pieces without a click at the joins. This is what













`NEUROSIS.CFG`'s `FilterOn` / `FilterOff` / `FilterIsOn` / `FilterChange` /













`BassFilter` reach.



























**`1650` — the period-to-note table.** `src/VTNOTES.PAS`. Answers all 2048













possible periods once at startup into `DS:$25c6`, packing the answer twice per













word: high byte `Oct*16 + Note`, low byte `Oct*12 + Note`. Both of its linear













searches fall off the end deliberately and answer "octave 0, note 0" rather













than running past the table.



























**`14b7` — control-block init**, and the first thing the chain calls that is













not the RTL:



























    FillChar(DS:$22c6, $300, 0);   DS:$24cc := $FF



























So **the control block is 768 bytes**, `1caa:22c6`..`1caa:25c5`, and the













dispatcher pointer the demo fetches at `CB+$121` sits inside it.



























**`188f` — resize the program's memory block.**



























    BX := (Bytes + 15) shr 4 + EndSeg - DS:$0c62;   ES := DS:$0c62













    AH := $4A;  INT 21h



























`DS:$0c62` is the segment DOS gave the program. This is the shrink before













going resident.



























**`116a` — add a path separator.** Appends a backslash to a `String` unless













its last character is already `:`, `\` or `/`.



























**`164b` — a format recogniser.** Sets `Obj^[$5d] := 4` (four channels), then













compares six characters against `'JMPLAY'` at `1caa:040e` and sets `Obj^[$59]`













to 6 or 0. One of a family — see the extension list below.

## Three more



























**`1642` — ASCIIZ to a fixed-width String.** `src/VTZSTR.PAS`. Copies up













to the NUL, truncates past the width, space-pads short of it, and writes the













length byte as the width regardless. Module formats hold their title and













sample names as fixed-length NUL-padded fields; this is what makes one

parameters and `RETF 6` removes only the parameters.

## `1b24` — the 8259

























DemoVT's own, and needed by any card that raises an IRQ.

























    1b24:0000  unmask IRQ N       1b24:0044  mask IRQ N

























Both take a Word and split at 8: below that they clear or set the bit in the












master mask at port $21; at or above it they do the same in the slave mask at












port $A1, and unmasking additionally clears bit 2 of the master so the cascade












is open. 768 bytes in the segment, so there is more here than these two.

## The driver model























`1a17:02ba` is what `1084`'s init hands its descriptor to, and it settles how











the whole sound side is put together.























```











RegisterDriver(D)                              1a17:02ba, RETF 4











    D^.Next  := DS:$0c02          the list head, at offset $36 in the record











    DS:$0c02 := D                 push it on the front











    if DS:$0b96 = nil then 1a17:018c(D)        nothing selected yet -- take it











    Inc(DS:$0b94)                 the count











```























So the drivers are a **singly-linked list**, each record carrying its `Next`











at offset `$36`, built at startup as each driver unit's initialisation runs.











Three variables hold it:























| | |











|---|---|











| `DS:$0c02` | head of the list |











| `DS:$0b94` | how many are registered |











| `DS:$0b96` | **the one currently selected** |























And `DS:$0b96` is exactly the object the timer polls — `1000:0171` does











`LES DI,[0b96] / CALLF [DI+$2a]` four times a tick, and INT 2Fh function 2











does it once. So "poll the driver" means "poll whichever driver is selected",











and the `[VT-SBlaster]` / `[VT-GUS]` / `[VT-DAC]` family are entries on this











list. Two virtual slots are known so far:























    +$1a   called by PlayModule at 1000:0302











    +$2a   the poll, called by the timer and by INT 2Fh function 2























## The output buffer and the 64K rule























`1a17:053c`, the startup the body calls at `1000:05d2`:























```











DS:$4312 := 1a17:0000     two hook slots, set to do-nothing defaults











DS:$4316 := 1a17:0001











DS:$430a := DS:$0c44      the output buffer











Linear   := Seg(Buf) shl 4 + Ofs(Buf)          done in 32 bits











if Linear + DS:$0ba4 > $10000 then











  DS:[BP-$12] := $10000 - Linear











```























That is **8-bit DMA boundary handling**: a transfer cannot cross a 64 KB











physical boundary, so the code works out the buffer's linear address and how











much of it fits below the next boundary. It confirms the two variables











`1000:03da` already implied — `DS:$430a` is the output buffer and `DS:$0ba4`











its size — and adds `DS:$0c44` as the pointer it was allocated at.

## The driver record, pinned down





















Two units register a driver, `1084` and `1065`, and both write **eight far










pointers into consecutive slots** and then hand `RegisterDriver` a pointer










that sits exactly `$16` below the first of them:





















| | `1084` | `1065` |










|---|---|---|










| descriptor | `DS:$0060` | `DS:$001e` |










| first slot | `DS:$0076` | `DS:$0034` |










| difference | `$16` | `$16` |





















So the record is a header of `$16` bytes, eight far method pointers from










`+$16` to `+$35`, and `Next` at `+$36` — which is the very next slot after










the last pointer, and matches what `1a17:02ba` writes. That closes the loop:





















| offset | who calls it | in `1084` |










|---|---|---|










| `+$16` | | `1084:0055` — clears a byte through a pointer parameter |










| `+$1a` | `PlayModule`, `1000:0302` | `1084:0061` — returns a Byte from `1723:04f1` |










| `+$1e` | | `1084:0072` — **start**: sets a hook, works out a divisor, `1723:0140` |










| `+$22` | | `1084:00f5` — empty |










| `+$26` | | `1084:00e4` — returns its argument unchanged |










| `+$2a` | **the timer, and INT 2Fh function 2** | `1084:004c` — `Inc(DS:$0bd0)` |










| `+$2e` | | `1084:00fc` — empty |










| `+$32` | | `1084:00d5` — **stop**: `1723:029f`, `1723:0357` |





















`1065` fills the same eight slots, but one of them — `+$2a`'s neighbour at










`+$2e` — points at **`1a17:1008`, inside the player core** rather than its own










segment, so the core supplies a shared default for methods a driver does not










need to override.





















### Which driver ends up selected





















`RegisterDriver` pushes onto the front of the list but only *selects* a driver










when none is selected yet, so **the first one registered wins**. The init










chain runs `1084` before `1065`, so `1084`'s is the default.





















`1084`'s poll does nothing but increment a counter, which is what a null










driver would do — but its start and stop both call into `1723`, which a null










driver would not. Its identity is left open rather than guessed at; `1723` has










not been read.





















### A number worth keeping





















`1084:0091` computes





















    (2_000_000 div (DS:$0bcc * 320)) + 1





















and then `256 - that`, before handing it to `1723:0140`. `DS:$0bcc` is a rate.

## `1084` + `1723` are the Gravis UltraSound



















The identity left open earlier is settled, on three independent pieces of









evidence.



















**The port scan.** `1723:04f1` walks a table of twelve candidate base ports at









`1caa:05a8`, indexed 1..12, writing each into `DS:$0582` and probing with









`1723:045a`:



















    $220 $240 $200 $210 $230 $250 $260 $270 $280 $290 $2A0 $2B0



















The two commonest first, then the rest in order. `DS:$0582` is the card's base









port from then on. A sentinel of `$FFFF` in `DS:$0582` means "not yet









scanned", and a scan that reaches entry 12 without a hit gives up and returns









false.



















**The register numbers.** `1723:0140` does, in order:



















    Write($47, Count)          GUS Timer 2 count









    DS:$0592 := DS:$0592 or $08









    Write($45, DS:$0592)       GUS Timer Control -- bit 3 is timer 2 IRQ enable









    DS:$0593 := DS:$0593 or $02









    OUT base+8, 4              Adlib-compatible timer control register select









    OUT base+9, DS:$0593       bit 1 starts timer 2



















`$45`/`$46`/`$47` are the UltraSound's timer control and its two counts, and









`base+8`/`base+9` are its Adlib command and data pair. `1723:0180` is the









mirror image: clear the enable bit, rewrite `$45`, clear the start bit,









rewrite the Adlib register.



















**The arithmetic.** `1084:0091` works out



















    256 - ((2_000_000 div (DS:$0bcc * 320)) + 1)



















and hands it to `1723:0140`. GUS timer 2 ticks every **320 microseconds** and









its preload counts up to 256, so `256 - n` is exactly how a GUS timer value is









loaded. The 320 is not a coincidence.



















There is a fourth, softer one: `1723:0539` computes `(X shl 9) and $1FFFFE00`









in 32 bits, which is the shape of a GUS DRAM voice address.



















So `[VT-GUS]` is `1084` (the driver record and its eight methods) sitting on









`1723` (the hardware). That also explains why `1084`'s poll does nothing but









`Inc(DS:$0bd0)` — on a GUS the card plays from its own DRAM and generates









its own timer interrupt, so there is nothing for the host to feed per tick.









The contradiction noted earlier resolves the other way from the guess: it is









not a null driver, it is a card that does not need the host.



















Since `1084` registers before `1065` in the init chain, and `RegisterDriver`









selects the first one registered, **the GUS is DemoVT's default when present**.

## `1891` is Borland's `Objects` unit

















The third RTL unit, and another 2.5 KB off the job. `1891:0000` is the object








allocator: it calls the RTL's allocate, reads the **size out of the VMT's first








word**, and zeroes everything past the VMT pointer — which is what








Turbo Pascal's `New(T, Init)` does and nothing else does.

















The clincher is the body's second call, `1891:03a7(1, 1, $7fe, DS:$0f82)`.








Turbo Pascal pushes `Self` last and the VMT offset just before it, so read








right to left that is

















    TCollection.Init(ALimit := 1, ADelta := 1)

















with `$7fe` as the VMT offset and `DS:$0f82` as `Self`. And the field offsets








agree: `TCollection` is VMT pointer at `+0`, `Items` at `+2`, **`Count` at








`+6`** — and `109c` reads the count from `DS:$0f88`, which is `$0f82 + 6`.

















So `DS:$0f82` is **the playlist**, a `TCollection`.

















RTL so far: `1ba1` (System), `1b6f` (Dos), `1891` (Objects) — about 7.6 KB








that does not get reconstructed.

## `19a0` is the Sound Blaster











`19a0:0000` is the **DSP reset**, and it is unmistakable:











```





OUT DS:$0afa, 1          assert reset





delay: 100 iterations of an empty loop





OUT DS:$0afa, 0          release it





repeat





  IN  DS:$0b04           read-buffer status





  IN  DS:$0afc           read data





until data = $AA or 100 tries





Result := (data = $AA)





```











The `$AA` handshake after a 1/0 pulse on the reset port is the Sound Blaster





DSP's signature and nothing else does it. That fixes four port variables:











| | offset from base | |





|---|---|---|





| `DS:$0afa` | `+6` | DSP reset |





| `DS:$0afc` | `+$A` | DSP read data |





| `DS:$0b02` | `+$C` | DSP write command/status |





| `DS:$0b04` | `+$E` | read-buffer status |











`19a0:005b` writes a DSP command, spinning on bit 7 of the write port until





the DSP is ready — `IN AL,DX / ADD AL,AL / JC` tests bit 7 by shifting it





into the carry, which is a byte shorter than `TEST AL,$80`.











So `19a0` is to `[VT-SBlaster]` / `[VT-SBPro]` what `1723` is to `[VT-GUS]`:





the hardware layer under a driver record. Which of the registered drivers





sits on it is not yet established — `1065` and `193a` are the candidates, and





both defer their poll to the core.











## `142f` — notes and effects











`142f:0000` takes two records, one at `[BP+4]` and one at `[BP+8]`, and:











```





Voice^[$13] := 0





Period := Note^[1]                    a word





if Period = 0 then Period := Voice^[1]





Voice^[$14] := Period





Hi := Note^[5] shr 4                  the high nibble of the byte at +5





Idx := NoteOf[Period] and $FF         DS:$25c6 -- the table 1650 built





Voice^[$16] := RateTab[(Idx + Hi) * 2]        DS:$0414





Lo := Note^[5] and $0F                the low nibble





...





```











Two things worth keeping. First, it **reads `DS:$25c6`**, so this is the





consumer of the period-to-note table `1650` builds at startup, and it uses the





**low byte** — the linear `Oct*12 + Note` form, not the packed nibble one.





Second, the record at `[BP+4]` is a word at `+1` and a byte at `+5` split into





two nibbles, which is the shape of a **tracker pattern event**: a period and





an effect with its parameter.











**`DS:$0414` IS THE PERIOD TABLE, and `DS:$04bc` is not a second one.** Both are
168 bytes, adjacent, and 84 words each; `$0414` is the ProTracker period table
(1712 down to 14 over seven octaves) indexed FLAT by the linear note, and `$04bc`
holds the GEOMETRIC MIDPOINTS between its adjacent entries:

    NoteBounds[i] = round(sqrt(NotePeriods[i] * NotePeriods[i+1]))

checked across all 83 pairs, no exceptions. That is why `1650` compares against
`$04bc` and takes the first entry the period does not exceed — the midpoints are
what make its search return the NEAREST semitone, and they have to be geometric
because pitch is logarithmic. So the two are one table's values and the same
table's boundaries, each indexed the way its own consumer wants: flat by `142f`,
by octave row by `1650` (`IMUL DI,Oct,$18`).

`142f:0000` is `StartArpeggio`, and this is the classic ProTracker arpeggio:
period → note → note plus semitones → period.

## `12ba` is the mixer, and it jumps into the middle of itself









The four patch sites make sense now. At `12ba:14c9`:









```




NEG AL / AND AL,7        how far into the block to start




MOV AH,$0F / MUL AH      times fifteen




ADD AX,$14D8 / JMP AX    and jump straight in




```









`$14D8` is the head of **eight copies of a fifteen-byte body**, and the entry




point is computed so a run of N samples starts N-mod-8 bodies from the end —




a computed-goto unrolled loop, the same trick as Duff's device. The body is:









```




MOV  AL,[SI]        fetch a sample byte




IMUL CL             scale it by the voice volume




MOV  ES:[DI],AX     store 16 bits




ADD  DI,BX          stride to the next output slot




ADD  BP,$4321       <- PATCHED: the fractional part of the step




ADC  SI,DX          carry into the integer sample index




```









2+2+3+2+4+2 = fifteen bytes exactly. `BP:SI` is a **16.16 fixed-point sample




position**: `ADD BP,step` accumulates the fraction and `ADC SI,DX` carries into




the index, so the sample rate conversion costs one add and one add-with-carry




per output sample and no division at all.









The immediate is patched rather than held in a register for the obvious




reason — every register is already in use (`AL` sample, `CL` volume, `SI`




source, `DI` destination, `BX` stride, `BP:SI` position, `DX` integer step,




`ES` output segment).









`12ba:148f` patches four of the eight bodies; the rest of the patcher runs on




past where the init disassembly stopped.









## `1a17:1008` — the shared poll, on its own stack









The routine `1065` and `193a` both point their `+$2a` slot at:









```




PUSHA / PUSH ES / PUSH DS




DS := the data segment




if CS:[$104b] <> 0 then bail          re-entrancy guard, held in CS




Inc(CS:[$104b])




DS:$4302 := SS;  DS:$4304 := SP       stash the caller's stack




SS := DS;  SP := $3f1a                and switch to a private one

CALLF [DS:$4312]                      the hook 1a17:053c installed
```

Two details worth having. It **switches to its own stack** before doing any

## Direct DAC output at `1a17:104d`









```




wait until the DSP write port's bit 7 clears




OUT DX, $10                     DSP command $10 -- direct DAC output




...




XOR AH,$80                      signed sample -> unsigned




wait for ready again




OUT DX, AH                      and write the byte




IN  from DS:$0bea, DS:$0bec     acknowledge




```









DSP command `$10` with a byte after it is the Sound Blaster's direct DAC




write, and `XOR AH,$80` is the signed-to-unsigned flip an 8-bit SB needs. So




the core carries a byte-at-a-time output path as well as the DMA one — which




is what a driver with no poll of its own would rely on.

## `1b24` in full — the PC's interrupt and DMA plumbing





Three jobs, all of them DemoVT's own code.





**Masks**, at `0000` and `0044`, already noted: unmask and mask an IRQ across


ports `$21` and `$A1`, opening the cascade when the IRQ is 8 or above.





**Vectors**, at `00d7`:





```


if IRQ < 8 then Vec := IRQ + 8 else Vec := IRQ + $68


GetIntVec(Vec, Old)        Dos, 1b6f:007b


SetIntVec(Vec, Handler)    Dos, 1b6f:0093


Result := Old


```





`$68 + 8 = $70`, so IRQ 0..7 map to INT `$08`..`$0F` and IRQ 8..15 to INT


`$70`..`$77`. Returning the displaced vector is what lets a driver put it back.


(That it reaches for `Dos.GetIntVec` here, having patched the `$2F` and `$1C`


vectors by hand elsewhere, is a nice inconsistency: the hand-rolled ones are


the two that need a chain.)





**DMA**, at `0128`:





```


AND AH,3                     the channel, 0..3 of the second controller


SHR CL,1 / RCR BX,1          halve address and count -- 16-bit DMA counts words


OUT $D4, AH+4                mask that channel


OUT $D8, 0                   clear the flip-flop


OUT $D6, AH+CH               mode


DX := AH*4 + $C0             the channel's address port


```





Ports `$C0`/`$D4`/`$D6`/`$D8` are the **second, 16-bit DMA controller**, and


the `SHR`/`RCR` pair halving a 32-bit quantity across `CL:BX` is the word-count


conversion 16-bit DMA needs.

## Options and config keys

`bfil`/`nobf`, `loop`/`nolp` and `flp`/`nofl` are on/off pairs, and `port`,

`DS:$4306` is written in exactly two places: here, where **Start points it at

the beginning of the output buffer**, and in the INT 2Fh dispatcher's case 3,

where it is set to wherever the hardware has actually reached, rounded down to

a multiple of four.



So `DS:$4306` is the **play position**, and function 3 is a **resync**: move

the position to now, snapshot `DS:$0bc8` into `DS:$0bca`, and clear the two

counters. That is the same reading as before, but now it rests on the variable

being identified from a second, independent site rather than on the shape of

the code alone.



`src/DEMOVT.PAS` in the main project can keep calling it `MusicFunc3`, but the

comment can now say what it does.

## `1723` — the GUS register interface, in full



Six small routines make up the whole hardware access layer, and every one of

them confirms the card.



```

1723:0000  SelectVoice(N)

1723:0030  Write(Reg, Val)      OUT base+$103, Reg   /  OUT base+$105, Val

1723:004a  ReadReg(Reg) : Word  if Reg < $40 then Reg := Reg or $80

                                OUT base+$103, Reg   /  IN AX, base+$104

1723:0065  WriteWord(Reg, W)    OUT base+$103, Reg   /  OUT AX, base+$104

1723:007d  Delay                seven IN AL, base -- the documented settle

1723:0140  StartTimer2 / 0180 StopTimer

```



`base+$103` is the register-select port and `base+$104`/`$105` the data pair,

which is the UltraSound's register interface exactly. Two details are pure

GUS: the **`or $80` on register numbers below `$40`** is the read-back flag the

card requires, and **seven successive reads of the base port** is the

prescribed inter-access delay. All four are `RET`, not `RETF` — near calls

inside the unit.



### `1723:045a` — the probe



```

CLI

Write($4C, 0);  Delay;  Write($4C, 7)      reset, then enable

Write($0E, $DF)                            active voice count

SelectVoice(0);  A := ReadReg($02)         save what is there

WriteWord($02, $16D8)                      poke a pattern

SelectVoice(1);  B := ReadReg($02)

WriteWord($02, $0F83)                      and a different one

SelectVoice(0);  if ReadReg($02) and $1FFF <> $16D8 then fail

SelectVoice(1);  if ReadReg($02) and $1FFF <> $0F83 then fail

Found := True

SelectVoice(0);  WriteWord($02, A)         put both back

SelectVoice(1);  WriteWord($02, B)

STI

```



Two different patterns into two different voices' address registers, read back

and masked to thirteen bits, then restored. That is the canonical UltraSound

detection and it cannot be anything else. `$4C` is the reset register, `$0E`

the active-voice count, `$02` a voice's address.



The whole thing runs with interrupts off and puts the registers back whatever

the outcome, so probing a machine that has no GUS at that port is harmless.



## `116e` — the option tokeniser



The routines from `116e:0000` split a `String` on a separator using the RTL's

`Pos` at `1ba1:0b7c` and `Copy` at `1ba1:0b0f`, working down a 256-byte local

copy and handing back the pieces. Together with `116e:04b2`, which lifts the

raw command tail out of `PSP:$0080`, that is the whole command-line front end:

fetch the tail, cut it into tokens, and let `109c` match the tokens against

its keyword list.

## `1caa` holds no code

Disassembling `1caa:0000` produces nonsense, and the prologue scan finds
nothing in all 3184 bytes. The segment is **constants only** — the strings and
tables already catalogued above (the name, `Silence`, the extension list, the
driver names, the ProTracker signatures, `JMPLAY`, the period table). Ghidra
calls it `CODE_30` because of where it sits in the image, not because there is
code in it.

That closes the segment out: nothing to reconstruct beyond the data.

## `193a` is a Sound Blaster driver

Two routines settle it.

`193a:0014` wires three port variables straight across:

```
DS:$0be8 := DS:$0b02        the DSP write port
DS:$0bea := DS:$0b06
DS:$0bec := DS:$0afe
```

and `DS:$0be8`/`$0bea`/`$0bec` are **exactly the three the core's direct-DAC
path at `1a17:104d` uses** — write, then two acknowledge reads. So this driver
hands the core the Sound Blaster's ports and lets the shared output path do
the work, which is why its `+$2a` slot points at `1a17:1008` rather than at
anything of its own.

`193a:0030` is its interrupt handler: interrupts off, registers saved, its own
data segment loaded, then

```
IN from DS:$0b06 and DS:$0afe        acknowledge the card
DS:$0b92 := 0
if DS:$0b90 <> 0 then ... else call 19a0:052b
```

with `19a0` being the SB hardware layer identified earlier. So the pairing is
the same shape as the GUS one:

| driver record | hardware layer | card |
|---|---|---|
| `1084` | `1723` | Gravis UltraSound |
| `193a` | `19a0` | Sound Blaster |
| `1065` | its own | something on IRQ 4 / port `$3F8` |

## `12ba:10a1` — the play range

`PlayModule` calls this with the loaded module:

```
CLI
DS:$02c4 := Song
DS:$033c, $033e, $0340 := DS:$0342, $0344, $0346
if DS:$0340 = 0 then DS:$0340 := Song^[$35]      fall back to the module's own
if DS:$033c = 0 then DS:$034c := 1 else DS:$034c := DS:$033c
if DS:$034c > DS:$0340 then give up
if DS:$033e = 0 then ... Song^[$37] ...
```

`DS:$0342`/`$0344`/`$0346` are the three values `PlayModule` copies out of
`DS:$08c2`/`$08c4`/`$08c6` at `1000:03e2` — so they come from the options, and
this is **start position, end position and length**, each falling back to the
module's own header fields (`[$35]` and `[$37]`) when the option was not given.

That is what `NEUROSIS.CFG` is doing when it gives each demo part its own
slice of a module to play.

## Three last readings

**`142f:0273` — effect nibbles.** The byte at a pattern event's `+5` is split
and applied according to a per-voice mode at `Voice^[$1a]`:

```
Lo := Note^[5] and $0F
if Lo <> 0 then
  case Voice^[$1a] of
    0, 1 : Voice^[$1c] := Lo
    2    : Voice^[$1c] := (Lo * $FF) shr 7      rescale 0..127 to 0..255
  end
Hi := Note^[5] shr 4
if Hi <> 0 then ... Hi shl 2 ...
```

So `+$1a` selects how the parameter is interpreted and `+$1c` receives it —
the two halves of a tracker effect column, handled separately as they should
be.

**`11bb:0020` — trim.** Strips leading characters that appear in a set held at
`CS:$0000`, by repeatedly taking `Copy(S, 2, 255)`. That the segment's first
bytes are that set is why disassembling `11bb:0000` desyncs.

**`165a:012a` — copy a sample descriptor.** Frees whatever the object held,
allocates `$1C` bytes through the manager at `DS:$39ae`, copies the source
record in, and then

    if Rec^[$0c] > $3F then Rec^[$0c] := $3F

**63 is ProTracker's maximum volume**, so `165a` handles **sample/instrument
descriptors** — 28 bytes each, with the volume clamped on the way in. That
fits the `+6` far pointer the other `165a` routines test.
