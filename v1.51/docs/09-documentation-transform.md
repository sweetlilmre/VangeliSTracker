# The documentation transform: apparatus and explanation

**Companion to `adr/0001-documented-source.md`.** The ADR proposed the design; this records what running it across all 34 units actually cost and actually found, in the form somebody starting the same job on a different target would want it.

A byte-exact reconstruction's source answers *how do we know this byte is right*. A reader wants to know *what the program does*. Both answers live in the same comments, and no single copy serves both. This is the transform that separated them.

## Result

| | |
|---|---|
| Units transformed | 34, in 30 commits |
| Tagged paragraphs stripped | 1,071 |
| Address-only comments dropped | 1,996 |
| Prefixes trimmed | 812 |
| Comments still naming an address, after | **0** |

| Linked image, both trees | **0 differing bytes** |

| Expired premises found | **14** |

## The problem is not filtering. It is a tangle.

The first attempt stripped **addresses** and stopped there: 2,000 address-only comments dropped and every word of reasoning behind them left standing. What came out was a file with 59% of its lines inside comments, almost none of which explained the program.

Counting the source's comments is what showed why:

| Of 4,218 comments in `src` | Count | Treatment |
|---|---|---|
| No apparatus signal at all | 2,121 | Carry through untouched — **no edit needed** |
| Short address-only citations | 1,431 | Drop mechanically, nothing lost |
| **Evidence and explanation in one comment** | 666 | Hand surgery — 499 of them full paragraphs |

Half the comments need nothing. A third drop for free. The remaining **666 are the whole job**, and no pattern can split them, because the sentence citing an address is frequently the same sentence explaining the design.

## Five decisions that make it survivable

### One tree of record

Explanatory prose is authored **in `src`**, beside the apparatus. `clean-src` is *derived* and regenerable, never hand-edited. Seeding a second copy once and editing it thereafter strands it the moment `src` moves — and `src` moved six times in one day that week.

### Keep by default; strip by mark

A tagged paragraph is apparatus and is stripped; everything else survives. That is what makes 2,121 comments free, and it fixes the direction of the failure mode: an untagged paragraph leaks an address, which a checker can see, rather than being silently deleted, which nothing can.

### Two mechanisms, two blind spots, and a gate instead of an argument

The pattern-dropper handles pure citations; the tag handles the tangle. That is deliberately two mechanisms, and in the same week it produced a real defect: a trimmed prefix left `{$FFFF ... }`, which Turbo Pascal reads as the far-calls **compiler directive**. `clean.py`'s own self-check is structurally blind to it, because it blanks every comment in both copies before comparing. What makes two mechanisms acceptable is the build, not care.

### The checker reports what survives the stripper

Not what the stripper removed. `tagcheck.py` runs the strip, then looks for apparatus tells in the *output* — a `segment:offset`, a `DS:$` address, a `[BP-` frame slot, an instrument name, a `~~withdrawn~~` marker. Mechanical tells only; it says nothing about prose style and stays silent otherwise. Its count is the one progress measure in the exercise that is not self-reported.

Two exemptions earned their place: the `[1.39b]` release quotes, and the `GENERATED by` banner — flagging that banner pushes towards deleting the one line telling a reader not to edit a generated output.

### `clean-src` must still build byte-identical

`build.py cleanbuild.toml`, then `linkbytes.py`: 0 differing bytes. Documentation that compiles differently from the program it documents is worse than none, and this check has already caught a defect nothing else could see.

## The mark, and its grain

The grain is the load-bearing detail: **the stripper and the checker must agree on where a paragraph begins and ends**, or the report names something the stripper does not remove.

| Language | Paragraph grain | What a tag carries with it |
|---|---|---|
| Pascal `{ }` | Blank-line separated | Its own *indented* continuations |
| Assembler `;` | Run of comment lines | Until a bare `;` ends the run |

Three marks, doing three different jobs:

* `[re]` — reconstruction apparatus. Stripped.
* `[reading]` — a claim resting only on someone's reading of the instructions. **Kept**, so a reader can tell a measured fact from an inference at a glance, and so inferences stay countable.
* `[1.39b]` — the author's own words about the author's own code. Kept, and the best explanatory content in the tree: *"If there is a loop, a small mess :-)"*, *"not sure this test is a good one"*. These are not apparatus.

The shape that results, purpose first, measurement surviving one paragraph lower under a tag:

```pascal
{ THE GAIN LADDER: 256 unrolled scale-and-add steps, one per volume
  level. On an 8086 a multiply is over a hundred cycles and this runs
  once per sample per channel, so the table is the difference between
  playing and not.

  [re] 1a17:0746..1a17:0b29, decoded from the image rather than typed.

  [re] THE WHOLE REGION IS ONE PROCEDURE, and it has to be. }
```

## The gate, run once per unit

One unit per commit. Every step is mechanical except the first two, and those two are where the value is.

1. **Rewrite every header purpose-first.** First sentence says what the thing is *for*. No routine left bare, so a missing header never means "not done yet"; trivial accessors get one obvious line and are allowed to be obvious.
2. **Tag the apparatus — extend, never replace.** Carry the text you found into a tagged paragraph **verbatim**. Rewriting a block is how measurements get deleted.
3. **Scan for syntax the language will not warn about.** Pascal `{ }` do not nest. A brace-depth pass over the file, not a careful read.
4. **Regenerate `clean-src`** — `clean.py src clean-src`, which verifies not one line of code differs.
5. **`tagcheck.py` clean on the unit** — 0 untagged paragraphs carrying apparatus.
6. **Build both trees** — `cleanbuild.toml` and `build.toml`, separately.
7. **`linkbytes.py link.toml` on each** — 0 differing bytes. The only check that reads what the compiler read.
8. **Commit the unit, and write down what you learned.** One unit, one commit, one message saying what the unit is for and what the pass turned up. The log becomes the audit trail — and it was the only surviving record of the first few expired premises.

**Order the units deliberately.** Two small self-contained units first — `ASCIIZ` and `FILTERS` — to settle the tag convention and the header voice against something cheap, then stop and review before the spine. Getting the convention wrong on `PLAYMOD` costs 1,400 lines of rework. Both pilot units took under an hour; `PLAYMOD` took three passes and two commits.

## What it actually found

**Fourteen claims in `src` that had stopped being true.** Not one was findable by any tool in the project, because a stale claim compiles.

| The claim, verbatim | What was true |
|---|---|
| `THIS UNIT DOES NOT COMPILE YET` | Two units. Both compiled. |
| `IT IS STILL NOT A COMPILABLE TRANSCRIPTION` | It was, and had been for weeks. |
| `STILL A STUB` | Three routines. All had full bodies. |
| `Its body is a PLACEHOLDER until the transcription reaches 132f` | Complete, 2,200 lines below. Same for `13d7`. |
| `NOT TRANSCRIBED YET. PLAYMOD.ASM currently holds a stub` | 679 lines. No stub. |
| `IN PROGRESS: transcribed as far as 070d` | Two routines, both finished. |
| `MaxChannels` is 8 here | It is 16 — forty lines above, in a comment explaining how that was measured. |
| `NOTHING BELOW IS A STUB ANY MORE` … `The bodies are deliberately wrong.` | Three stale claims in one block, the first contradicting the last. |
| `NOT TRANSCRIBED` … `THE OPEN QUESTION` | Answered four paragraphs later under `RESOLVED`, above a complete 664-byte body. |
| `BLOCKED` labels in both `build.toml`s | Nothing was blocked. |

The pattern is worth stating plainly. Code in this project is checked from every angle — bytes by `linkbytes`, sizes by `units`, layout by `dgroup`, order by `linkorder`, addresses-in-prose by `dsverify`. **Everything else in the prose is checked by nothing.** Edit a sentence to say the opposite of what the code does and every instrument still passes.

Rewriting a header is the only operation that forces every sentence to be read against the code it sits above. That is why the transform's real yield was not the documentation. It was the audit.

**The worst shape is prose that argues *from* a stale fact.** A wrong number in a comment is a wrong label. A wrong number reasoned from reads as corroboration for itself, survives review better than the bare comment would, and no mechanical fixer can reach it — correcting the declaration leaves the paragraph beside it still arguing from the old value. See `kit/wiki/observations/comments-are-unchecked-claims`.

## Hazards, and the fix for each

Every row cost real time. Four of them silently changed code while a comment was being edited, which is the entire reason the byte-compare is in the gate.

| Hazard | Hit | How it showed, and the fix |
|---|---|---|
| Rewriting a comment block | 4× | Deleted 52 measured addresses at a stroke in `FILTERS.PAS` by replacing prose instead of extending it; then again in `VTDRIVER`, `VTDOSRSZ` and `VTGAIN`. **Fix:** append; carry found text verbatim into a tagged paragraph. |
| Shell heredocs and backslashes | 4× | Assertion failures, `IndentationError`, `SyntaxError` — and once **silently**: `\b` became a literal `\x08`, the pattern compiled, the flags were right, and it matched nothing forever. **Fix:** any script containing a regex goes through the Write tool, never a heredoc. |
| Comments that do not nest | 3× | A `{ }` inside a `{ }` in an equivalent-Pascal block. Caught by a brace-depth scan; never by reading. **Fix:** put the scan in the gate. |
| Tagging by line number | 2× | Once it prefixed a live statement — `[re] SetVTDevice;` — and **the build caught it and nothing else would have**. Once it produced `{ [re] $G+}`, breaking a compiler directive and **silently disabling 286 codegen**. **Fix:** refuse any line opening `{$`, and require the insertion point to be inside a comment. |
| A guard that tested the wrong thing | 1× | "Is this inside a comment?" asked whether the *line contained* `{` — so `OutSlot0 : Word = 0; { DS:$0ca0 }` counted as inside. **Fix:** test the insertion point's nesting depth, not the line's characters. |
| Catastrophic backtracking | 1× | Nested quantifiers inside a lookahead hung `clean.py`; the process had to be killed and the file restored from git. **Fix:** an iterative scan, where the citation grammar is genuinely iterative. |
| `^` in a pattern used with `.match(s, pos)` | 1× | Anchors to string start, not to the offset, so citation continuations never matched. **Fix:** drop the anchor; `.match` already anchors. |
| Trusting a report as a key | 3× | Using `tagcheck`'s truncated, line-joined display as an exact-match string. Fails at the assertion, before the write — wasted, not dangerous. **Fix:** the report says *which* paragraph; the file says how to match it. |
| Editing a generated file | 1× | An earlier header pass had left `emit_gain.py` with an `IndentationError` nothing had run since. **Fix:** edit the generator *and* its outputs in one commit, and exempt the `GENERATED by` banner from the checker. |
| `sed -i` on CRLF files | 1× | Converted five scripts to LF, producing whole-file diffs. **Fix:** restore from `git show HEAD:`, and read/write with explicit `newline=''`. |

## Carrying it to another target

Four questions decide whether the method arrives intact. The first is not optional.

### 1. Is there a mechanical "the code did not change" check?

On a byte-exact reconstruction the linked-image compare is the strongest link in the chain, and it earned its place: four hazards above are code changes made while editing a comment. **Without some equivalent, do not run this transform.**

Substitutes, in descending order of strength, where there is no full rebuild:

* assemble or compile the touched region and compare the bytes;
* hash the code stream with every comment blanked, and require the hash to hold;
* at minimum, diff the file with all comments stripped and require zero changed lines — which is cheap, and is what `clean.py`'s self-check already does.

### 2. What is the paragraph grain?

Decide it before writing a single tag, and encode the *same* grain in both stripper and checker. Pascal's braces gave blank-line paragraphs; `PLAYMOD.ASM` and `SOUNDDEV.ASM` have no blank lines at all, so their grain became a run of comment lines terminated by a bare `;`. A target in C, or a different assembler, needs its own answer — and a mixed-language tree needs one answer per language, in both tools.

### 3. What can a claim rest on?

Here it was, in order: the 1.39b release source, the `DEMOVT15` client bindings and `DEMOVT.DOC`, format specifications, hardware documentation, the call sites, and last the instructions themselves. Anything resting only on a reading of instructions gets `[reading]`, so the inference count is visible rather than invisible.

Where a target has no later release to lean on, expect that count to be much higher. That is fine, provided it is *counted* — and it makes the `[reading]` tag more important, not less. The standing constraint is unchanged: no loader implementation source may be read, quoted or adapted. Format facts only.

### 4. What is a unit?

A unit is whatever makes one commit reviewable. Thirty-four source files gave it for free. A single monolithic binary does not, so invent the boundary — one segment, one routine group, one feature — and keep it small enough that a bad convention costs an afternoon rather than a week. And look for generated files **before** starting, not after editing one.

## What to do differently next time

* **Write the two guards before the first unit.** The brace-depth scan and the line-number insertion guard each exist because something broke first. Both are twenty lines.
* **Record the checker's tree-wide count on day one.** 885 → 0 was the only honest progress measure in the whole exercise; every other signal was self-reported.
* **Log expired premises as a deliverable from the start.** Counting began at four, and the earlier ones had to be reconstructed from commit messages. They are the highest-value output of the transform and deserve their own list, not a mention in a commit body.
* **Keep the two-pilot-units rule.** It was written down in advance, it felt like a delay, and it is why the spine units went through in one pass each.
